# DuckDB 2.0.0: characterization facts

What DuckDB's own sqllogictests (`test/sql/` at `v2.0.0`) and the fuzzer
say about DuckDB, compared with the reference model (`Rel.eval`). Each fact
names its evidence: ledger entries (`<area>.json`, by test file and line)
and fuzz findings (`fuzz__<target>.json`). The ledgers and the summary
table in [README.md](README.md) are generated by `python -m sverify.slt`
and `python -m sverify.duckdb_fuzz`; this file is written by hand from them.

Facts come in three kinds:

- **Model**: the SQL standard (ISO/IEC 9075-2) or the Substrait spec decides,
  and `Rel.eval` does something else. These are ordinary Lean fixes.
- **Profile**: DuckDB's behaviour where the standard leaves a choice, or
  where DuckDB departs from it. These become rules of DuckDB's profile.
- **sverify**: a gap in sverify's own frontends, written plans or harness,
  not in the reference semantics.

Counts are the ledger entries that show the fact. A count is evidence, not
coverage: one test file often repeats a query per type.

of months, `DuckDB-specific` typing, the `UUID` type).

## Model: the reference model disagrees with the standard

### M1. Integer overflow gives the unbounded value

`Rel.eval`'s integers are unbounded, and `UnFn.wrap n` (arithmetic on
`TINYINT`, `SMALLINT`, `INT`) is the identity ([`SubstraitLean/Expr.lean:134`](../../SubstraitLean/Expr.lean#L134)). So `9223372036854775800::BIGINT + 5000::BIGINT` is
`9223372036854780800` and `100::TINYINT + 50::TINYINT` is `150`. The
standard raises *data exception: numeric value out of range* (SQLSTATE
22003) when a result is not representable in its type. DuckDB raises
`Out of Range Error: Overflow in addition of INT64` at every width.
`verify` reports these as `may wrap around`, a warning.

Evidence: `overflow/integer_overflow.test`, `overflow/bigint_overflow.test`,
`overflow/table_overflow.test`, `overflow/test_overflow.test`,
`function/operator/test_division_overflow.test` (`MIN // -1`),
`optimizer.json` (`-v` of a `TINYINT` −128); fuzz: `fuzz__int_overflow.json`
(`+`, `-`, `*`, negation, `abs(-2⁶³)`, `-2⁶³ / -1`), `fuzz__int_division.json`.

### M2. Division and remainder by zero give NULL

`BinFn.idiv`/`imod` return `NULL` for a zero divisor
([`SubstraitLean/Expr.lean:195`](../../SubstraitLean/Expr.lean#L195)). The standard raises *data exception: division
by zero* (22012). DuckDB 2.0 raises `Division by zero` for `/`, `//`, `%`
and `mod()` on every numeric type, doubles included
(`error_on_division_by_zero` defaults to true; with it false, DuckDB
returns NULL). `verify` reports `division by zero` as an error, and the
written plan's guard raises on DuckDB, so only `Rel.eval` itself is off.

Evidence: `function/operator/test_division_by_zero.test`,
`function/numeric/test_mod.test`, `function/numeric/decimal_mod.test`;
fuzz: `fuzz__int_division.json`.

### M3. A cast to a narrower integer that does not fit gives NULL

`UnFn.narrow n` returns `NULL` where the value does not fit
([`SubstraitLean/Expr.lean:133`](../../SubstraitLean/Expr.lean#L133)). The standard
raises 22003; DuckDB raises `Conversion Error: Type INT32 with value 200
can't be cast …`. A constant cast is caught: the checker refuses
`CAST(200 AS TINYINT)` (`cast of 200 to a 8-bit integer overflows`).

Evidence: `overflow/test_overflow.test:54`, `overflow/table_overflow.test:154`.

### M4. `%` on doubles is integer remainder on float codes

`"modulus"` always parses to `.bin .imod` ([`SubstraitLean/Parse.lean:956`](../../SubstraitLean/Parse.lean#L956),
in `mkCall`); `mkFloatCall` ([`Parse.lean:1032`](../../SubstraitLean/Parse.lean#L1032))
has no `modulus` case. On doubles `imod` works on
the float codes, so `7.5 % 2.0` evaluates to a 300-digit integer, and
`d % 0.0` to NULL. Substrait's `modulus` on `fp64` is the IEEE remainder
(`fmod`): `7.5 % 2.0 = 1.5`, and `% 0.0` is NaN. DuckDB agrees with
Substrait. This is a soundness bug: the plan is accepted and the result is
wrong.

Evidence: `function/numeric/decimal_mod.test:5,10,16`,
`function/numeric/test_mod.test:11`, `function/operator/test_division_by_zero.test:87,113`,
`types/float`; fuzz: `fuzz__float_arith.json`, `fuzz__int_division.json`
(`d % d` with `d = 0.0`).

### M5. `SUM` of a constant double sums float codes

`SELECT SUM(CAST('inf' AS DOUBLE))` evaluates to a 500-digit integer: the
aggregate takes its argument for an integer when it is a cast of a string
constant, and adds the codes. `SUM` over a double column is right. A
soundness bug.

`avg(42) OVER ()` is `inf` the same way.

Evidence: `types/float/nan_aggregates.test:7` (`SUM('inf'::DOUBLE)`,
`SUM('nan'::DOUBLE)`), `window/test_scalar_window.test:11`.

### M6. `CAST(<date literal> AS TIMESTAMP)` keeps the day count as microseconds

A date literal is an integer in the model (`argKind`,
[`Parse.lean:833`](../../SubstraitLean/Parse.lean#L833)), so the cast takes the
`.int → .time` branch, `asTime` ([`Parse.lean:1248`](../../SubstraitLean/Parse.lean#L1248)), which reads the integer as
microseconds: `CAST(DATE '2020-05-05' AS TIMESTAMP)` is
`1970-01-01 00:00:00.018387`. The standard's cast of a date to a timestamp
is midnight of that day. The other direction keeps the code too:
`(TIMESTAMP '1992-01-01 01:01:01')::DATE` is the microsecond count. So
`ts >= DATE '1993-08-15'` compares microseconds with days and keeps
`1993-08-14`, and DataFusion's `COALESCE(date, timestamp)` mixes the two
codes. A soundness bug.

Evidence: `types/date/date_implicit_cast.test:13`,
`types/timestamp/test_timestamp.test:119,139`,
`function/generic/test_if_null.test:15`, `function/generic/test_if.test:20`.

### M7. Ordering comparisons of lists are NULL

`[1, 2] < [1, 3]` evaluates to NULL on every row (equality works). The
standard and DuckDB compare lists element by element. The model should
either refuse the comparison or define it; returning NULL silently is a
soundness bug.

Evidence: `types/list` (`SELECT l < r FROM list_int1` and the other
ordering operators).

### M8. Double division by zero gives ±∞ or NaN

`fdiv` follows IEEE 754 (`1.0 / 0.0 = inf`). The standard's
division-by-zero exception covers approximate numerics too, and DuckDB 2.0
raises. This is the same rule as M2 for doubles; Substrait's `divide` has an
`on_division_by_zero` option (`IEEE`, `NULL`, `ERROR`), so the reference can
pick `ERROR` and a profile can declare `IEEE`.

Evidence: `function/operator/test_division_by_zero.test:73,98,108`;
fuzz: `fuzz__float_arith.json` (`d / d` with `d = 0.0`).

## Profile: DuckDB's own behaviour

### D1. Integer arithmetic is checked at the declared width

DuckDB raises on overflow of `+`, `-`, `*`, unary `-`, `abs`, and of `//`
for `MIN // -1`, at the width of the result type: `TINYINT` arithmetic
fails past 127. An integer literal takes the narrowest type that holds it,
so `100::TINYINT + 50` is a `TINYINT` addition and fails. `//` truncates
toward zero (`-7 // 2 = -3`) and `%` takes the sign of the dividend
(`-7 % 2 = -1`, `7 % -2 = 1`), as `Int.tdiv`/`Int.tmod` do. This matches
the reference once M1 and M2 are fixed.

### D2. `/` on integers is float division

In DuckDB's SQL `7 / 2 = 3.5` and `//` is integer division; the setting
`integer_division` switches `/` to `//`. This is the SQL frontend's
choice, not the plan's: the replay translates DuckDB's `/` to a double
division before planning, and the fuzzer sets `integer_division`.

### D3. Casts to integers round half away from zero

`CAST(0.55 AS INTEGER) = 1`, `CAST(-0.55 AS BIGINT) = -1`, for decimals and
doubles alike; `avg(d)::INTEGER` rounds too. Lean's `ftoi` (and DataFusion)
truncate. The standard leaves rounding or truncation to the implementation
when an exact or approximate numeric loses digits, so this is a profile rule.

Evidence: `cast/decimal_integer_cast.test`, `cast/float_integer_cast.test`,
`function/numeric/test_floor_ceil.test`, `aggregate/…/test_combine_aggr.test:18`.

### D4. Division by zero is an error, configurably

`error_on_division_by_zero = true` (the 2.0 default) raises; `false`
returns NULL for integers and IEEE values for doubles. A DuckDB profile
rule has this setting as a parameter.

### D5. `-0.0` and `0.0` are distinct

`ORDER BY` puts `-0.0` before `0.0`, and `1.0 / -0.0 = -inf`. The model has
one zero (#89).

Evidence: `order/…:28` (`SELECT v, 1.0 / v FROM zero_probe`).

### D6. `FLOAT` is 32 bits

`2e38::FLOAT / 0.1` is `inf` and `1e308::FLOAT` fails to convert. The
model has one double kind. Evidence: `overflow/double_float_overflow.test:43`,
`cast/double_float_cast.test`, `overflow/test_numeric_overflow.test:11`.

### D7. `SUBSTRING` with a negative start counts from the end

`substring('hello' FROM -2 FOR 2) = 'lo'`. The standard's `SUBSTRING`
takes positions before 1 as empty (`''` here), as Lean and DataFusion do.
Evidence: `function/string/test_substring.test:129,207`.

### D8. NULLs sort last in both directions

DuckDB's default `NULLS LAST` holds for `DESC` too; DataFusion's SQL (and
so the plans sverify writes) puts NULLs first for `DESC`. The replay writes
the order out explicitly (`translate`), and follows
`SET default_null_order`. Frontend, not plan semantics.

### D9. Collations, macros and case-insensitive names

DuckDB compares under a column's collation (`NOCASE`, `NOACCENT`) and lets
macros shadow functions. The replay skips queries once a test uses one.
Unquoted identifiers are case-insensitive, which the replay follows.

## sverify: frontends, written plans and the harness

### S1. The written plan types literals by their value (#96)

`LEAST(DATE '1992-01-01', …)` on DuckDB returns `7670`, and timestamp and
interval literals come back as integers. Evidence:
`function/generic/test_least_greatest.test:69-95`, `types/date`,
`types/timestamp`, `types/interval` (the `engine` side).

### S2. The written plan computes narrow integers in 64 bits

`100::TINYINT + 50::TINYINT` on the written plan gives 150 on DuckDB (DuckDB
itself raises): `sql/duckdb.py` writes the arithmetic without the narrow
type. Evidence: the `both` entries of `overflow.json`.

### S3. DataFusion's producer drops `VALUES` rows

DataFusion 51 writes `FROM (VALUES …)` as an empty virtual table, so the
plan reads no rows. The replay refuses these plans
(`producer: VALUES written as an empty virtual table`).

### S4. Decimal literals become doubles

DataFusion's SQL reads `99999999999999999999.99999` as a double, so
`100000000000000000000 > 99999999999999999999.99999` is false. Evidence:
`cast/decimal_float_cast.test:10`.

### S6. DataFusion's SQL frontend plans another query

In these cases `Rel.eval` and DuckDB running the written plan agree with
each other, and both differ from DuckDB, because the plan DataFusion writes
is not the query. Each one is a plan sverify checks for a query the user
did not write.

- `EXCEPT ALL` is planned as a left anti join, i.e. without multiplicities:
  `[1, 1, 2, 3] EXCEPT ALL [1, 3]` gives `[2]`, not `[1, 2]`
  (`setops/test_pg_union.test:339,350`).
- `FETCH FIRST n ROWS ONLY` is dropped: the plan has no limit
  (`parser/fetch_first.test`).
- `DISTINCT` and `FILTER (WHERE …)` of a window aggregate are dropped by
  the Substrait producer: `COUNT(DISTINCT s) OVER (…)` counts every row
  (`window/test_window_distinct.test:76`, `window/test_naive_aggregation.test:204`,
  `window/test_streaming_window.test:223`).
- `GROUP BY k, k` writes two grouping expressions, and the projection above
  reads the aggregate's columns shifted by one (`aggregate/group/test_group_by.test:149`):
  either the producer or Lean's reading of a repeated grouping expression
  is wrong; this needs reading.
- `SELECT *` of a `NATURAL JOIN` keeps both copies of the join columns
  (`catalog/case_insensitive_using.test:123-138`).

### S5. What the replay cannot run

Most refusals are DuckDB features outside the model (structs, maps,
decimals, blobs, `range()`, `PIVOT`, DuckDB-only functions) or SQL that
sqlglot or DataFusion's SQL cannot read. The replay inlines only the values
`sverify.testing.literal` writes, so tables holding structs, decimals or
blobs are refused (`tables: no Lean literal`). Expected errors that are
DuckDB's binder or parser errors are skipped (`DuckDB frontend error`).
