# DuckDB 2.0.0: characterization facts

What DuckDB's own sqllogictests (`test/sql/` at `v2.0.0`) and the fuzzer
say, judged against the reference model's principles (#185, "Principles for
the reference model"):

- `Rel.eval` means **Substrait's semantics**: each function's extension
  YAML, including its options.
- Where Substrait leaves a choice open, the reference takes the least
  surprising one that every backend can emulate.
- DuckDB's profile is a **diff** against that reference.

Substrait here is the spec at `v0.108.0`: `extensions/functions_arithmetic.yaml`,
`functions_comparison.yaml` and `functions_string.yaml`.

The evidence is ledger entries (`<area>.json`, by test file and line) and
fuzz findings (`fuzz__<target>.json`). The ledgers and the summary table in
[README.md](README.md) are generated by `python -m sverify.slt` and
`python -m sverify.duckdb_fuzz`; this file is written by hand from them.

## What the plans say

The plans come from DataFusion 51's SQL producer. They set **no function
options** and no extension URNs: a call is `add`, `divide`, `modulus`, … by
name, with argument and output types. Casts do carry
`failureBehavior: FAILURE_BEHAVIOR_THROW_EXCEPTION`. So for every function
option below, the plan omits it and the outcome is the reference's default.
Those defaults are not decided yet.

Each finding is one of:

- **Deviation**: `Rel.eval` disagrees with Substrait whatever the omitted
  options are, for example a result outside its declared type. These are
  Lean fixes, to be made once the defaults are set.
- **Reference choice pending**: the outcome depends on an option the plan
  omits, or on something Substrait leaves open. The finding records the
  choices, which one `Rel.eval` makes today, and what DuckDB does.
- **sverify**: a gap in sverify's frontends, written plans or harness.

For each finding, the DuckDB diff says what DuckDB does natively, which
option values it implements as they are, and the shim that gets it to each
other value (or that the function must be refused).

## R1. Integer overflow of `+ - *`, negation, `abs` and `MIN / -1`

- **Substrait:** `add`, `subtract`, `multiply`, `negate` and `abs` on
  `i8`/`i16`/`i32`/`i64` return the same type and take `overflow: [SILENT,
  SATURATE, ERROR]`; `divide` on integers takes `overflow` too (for
  `MIN / -1`). Under every option the result is a value of the declared type
  (wrapped, clamped) or an error.
- **Lean:** `Rel.eval`'s integers are unbounded, and `UnFn.wrap n`, which
  marks arithmetic narrower than 64 bits, is the identity
  ([`Expr.lean:134`](../../SubstraitLean/Expr.lean#L134)). So
  `9223372036854775800 + 5000` is `9223372036854780800`, and
  `100::TINYINT + 50::TINYINT` is `150`. That is outside `i64` and `i8`
  under every option: a **deviation**. Which option applies when the plan
  omits it is **pending**. The parser accepts only `SILENT` for `+ - *`
  ([`Parse.lean:770`](../../SubstraitLean/Parse.lean#L770)), and `verify`
  reports `may wrap around` as a warning, so today's intent is `SILENT`,
  which `Rel.eval` does not implement.
- **DuckDB (native):** raises `Out of Range Error: Overflow …` at the
  declared width, `TINYINT` included, so `ERROR` is native. `SILENT` needs
  a shim: compute in `HUGEINT` and wrap to the width,
  `((x::HUGEINT + y + 2^(w-1)) % 2^w + 2^w) % 2^w - 2^(w-1)`, cast back.
  `SATURATE` needs a shim too: compute in `HUGEINT` and clamp,
  `LEAST(GREATEST(x::HUGEINT + y, MIN_w), MAX_w)`. `HUGEINT` holds every
  `i64` product, so both shims are exact.
- **Frontend (F3):** DuckDB gives an integer literal the narrowest type
  that holds it, so `100::TINYINT + 50` is an `i8` addition in DuckDB, and
  an `i64` one in DataFusion's plan.

Evidence: `overflow/integer_overflow.test`, `overflow/bigint_overflow.test`,
`overflow/table_overflow.test`, `overflow/test_overflow.test`,
`function/operator/test_division_overflow.test`,
`optimizer/expression/test_negation_limits.test`; fuzz:
`fuzz__int_overflow.json` (`+`, `-`, `*`, negation, `abs(-2⁶³)`, `-2⁶³ / -1`)
and `fuzz__int_division.json`.

## R2. Integer division by zero

- **Substrait:** `divide` on integers takes
  `on_division_by_zero: [NULL, ERROR]`, and truncates toward zero.
- **Lean:** `Rel.eval` gives NULL
  ([`Expr.lean:195`](../../SubstraitLean/Expr.lean#L195)), one of the two
  options, so this is **pending**. `verify` reports `division by zero` as an
  error (DataFusion's behaviour), so `Rel.eval` and `verify` currently make
  different choices.
- **DuckDB (native):** raises, under `error_on_division_by_zero = true`,
  the 2.0 default, so `ERROR` is native. `NULL` needs a shim,
  `CASE WHEN y = 0 THEN NULL ELSE x // y END`, or the setting
  `error_on_division_by_zero = false` for the whole query. Truncation is
  native: `-7 // 2 = -3`, in every agreeing entry and fuzz case.

Evidence: `function/operator/test_division_by_zero.test`; fuzz:
`fuzz__int_division.json`.

## R3. Integer `modulus`: zero divisor and sign

- **Substrait:** `modulus` on integers takes
  `division_type: [TRUNCATE, FLOOR]` (the remainder's sign),
  `on_domain_error: [NULL, ERROR]` (a zero divisor) and `overflow`.
- **Lean:** truncates (`Int.tmod`) and gives NULL for a zero divisor, both
  allowed options: **pending**.
- **DuckDB (native):** `%` truncates (`-7 % 2 = -1`, `7 % -2 = 1`) and
  raises on zero. So `TRUNCATE` and `ERROR` are native. `FLOOR` needs a
  shim, `x % y + CASE WHEN x % y <> 0 AND (x % y < 0) <> (y < 0) THEN y ELSE 0 END`.
  `NULL` needs the `CASE` of R2.

Evidence: `function/operator/test_division_by_zero.test:28,39,64`,
`function/numeric/test_mod.test:17`; fuzz: `fuzz__int_division.json`.

## R4. `modulus` on doubles

- **Substrait:** `functions_arithmetic.yaml` has no `fp32`/`fp64` impl of
  `modulus`. DataFusion writes `modulus` with `fp64` arguments anyway.
- **Lean:** `"modulus"` always parses to integer `imod`
  ([`Parse.lean:956`](../../SubstraitLean/Parse.lean#L956));
  `mkFloatCall` ([`Parse.lean:1032`](../../SubstraitLean/Parse.lean#L1032))
  has no case for it. On doubles, `imod` works on the float codes:
  `7.5 % 2.0` evaluates to a 300-digit integer, `d % 0.0` to NULL. A
  **deviation**, and a soundness bug, since the plan is accepted and the
  result is wrong. Until Substrait (or a sverify extension) defines it, the
  reference refuses the call.
- **DuckDB (native):** `fmod` (`7.5 % 2 = 1.5`, `% 0.0` is NaN, or an error
  with `error_on_division_by_zero`). Not needed while the reference refuses.

Evidence: `function/numeric/decimal_mod.test:5,10,16`,
`function/numeric/test_mod.test:11`, `types/float/ieee_floating_points.test:24`,
`types/float/nan_arithmetic.test:51`; fuzz: `fuzz__float_arith.json`,
`fuzz__int_division.json`.

## R5. Double division by zero

- **Substrait:** `divide` on `fp32`/`fp64` takes
  `on_division_by_zero: [IEEE, LIMIT, NULL, ERROR]` and
  `on_domain_error: [NAN, NULL, ERROR]` (`0/0`).
- **Lean:** IEEE (`1.0 / 0.0 = inf`, `0.0 / 0.0 = NaN`); the parser accepts
  only `IEEE` ([`Parse.lean:783`](../../SubstraitLean/Parse.lean#L783)).
  An allowed option: **pending**.
- **DuckDB (native):** raises for `x / 0.0` and `0.0 / 0.0`, so `ERROR` is
  native. With `error_on_division_by_zero = false`, DuckDB gives IEEE
  values for doubles (`7.0 / 0 = inf`), so `IEEE` is that setting, or a
  shim, `CASE WHEN y = 0 THEN x * 'inf'::DOUBLE …`, with care for `-0.0` and
  NaN. `NULL` needs a `CASE`. `LIMIT` needs a shim that clamps to
  `±DBL_MAX`.

Evidence: `function/operator/test_division_by_zero.test:73,98,108,181,186`;
fuzz: `fuzz__float_arith.json` (`d / d` with `d = 0.0`).

## R6. Integer `sum`

- **Substrait:** `sum` of `i8`…`i64` returns `i64?` and takes `overflow`.
- **Lean:** the sum is unbounded, which is a **deviation** past `i64`. The
  parser accepts `SILENT` (`sumWraps`), so the option is **pending**.
  `SUM(b)::BIGINT` of a sum past `2⁶³` is the unbounded value
  (`aggregate/aggregates/test_sum.test:74`).
- **DuckDB (native):** `SUM(BIGINT)` returns `HUGEINT` and never overflows
  at 64 bits. So no option is native at `i64`. `ERROR` needs a shim,
  `CAST(SUM(x) AS BIGINT)`, which raises; sverify's written plan already
  guards this and raises (`test_sum.test:68`). `SILENT` and `SATURATE` need
  the wrap and clamp shims of R1, applied to the `HUGEINT` sum.
- **Also:** Substrait's `avg` of `i64` returns `i64?`, while DataFusion
  writes `avg` with an `fp64` output, which matches no impl. **Pending**:
  refuse it, or read it as `avg` over the argument cast to `fp64`.

## R7. `sum`/`avg` of a double constant

- **Substrait:** `sum(fp64)` returns `fp64?`.
- **Lean:** `SUM(CAST('inf' AS DOUBLE))` evaluates to a 500-digit integer,
  and `avg(42) OVER ()` to `inf`. The aggregate takes a constant argument
  for an integer and adds float codes; over a double column it is right. A
  **deviation** and a soundness bug.
- **DuckDB (native):** IEEE sums (`inf`, `-inf`, `nan`).

Evidence: `types/float/nan_aggregates.test:7`, `window/test_scalar_window.test:11`.

## R8. A cast to a narrower integer that does not fit

- **Substrait:** the plan's cast says
  `failureBehavior: THROW_EXCEPTION`.
- **Lean:** `UnFn.narrow n` gives NULL
  ([`Expr.lean:133`](../../SubstraitLean/Expr.lean#L133)), while `verify`
  reports `cast out of range` as an error, and the checker refuses a
  constant one (`CAST(200 AS TINYINT)`). `Rel.eval` **deviates** from the
  plan. Whether "may raise" in `verify` is enough depends on how the
  reference represents errors (principle 4: an error as "may raise").
- **DuckDB (native):** `CAST` raises (`Conversion Error`), so
  `THROW_EXCEPTION` is native. `RETURN_NULL` is `TRY_CAST`, also native.

Evidence: `overflow/test_overflow.test:31,36,54`, `overflow/table_overflow.test:154`.

## R9. Casts of doubles and decimals to integers: rounding

- **Substrait:** the cast's rounding is not specified.
- **Lean:** truncates (`ftoi`), as DataFusion does. **Pending.**
- **DuckDB (native):** rounds half away from zero:
  `CAST(0.55 AS INTEGER) = 1`, `CAST(-0.55 AS BIGINT) = -1`, and
  `avg(d)::INTEGER` rounds too. Truncation needs a shim,
  `CAST(trunc(x) AS INTEGER)`.

Evidence: `cast/decimal_integer_cast.test`, `cast/float_integer_cast.test`,
`function/numeric/test_floor_ceil.test`,
`aggregate/aggregate_state_export/test_combine_aggr.test:18`.

## R10. Casts between date and timestamp literals

- **Substrait:** a `date` is a day, and a `precision_timestamp` a point in
  time. A cast from date to timestamp is that day at midnight.
- **Lean:** a date or timestamp literal is an integer in the model
  (`argKind`, [`Parse.lean:833`](../../SubstraitLean/Parse.lean#L833)), so
  `CAST(DATE '2020-05-05' AS TIMESTAMP)` takes the `.int → .time` branch
  ([`Parse.lean:1248`](../../SubstraitLean/Parse.lean#L1248)) and reads
  18387 days as 18387 µs. `(TIMESTAMP …)::DATE` keeps the microsecond count
  as days. Then `ts >= DATE '1993-08-15'` compares microseconds with days,
  and `COALESCE(date, timestamp)` mixes both codes. A **deviation** and a
  soundness bug.
- **DuckDB (native):** standard conversions.

Evidence: `types/date/date_implicit_cast.test:13`,
`types/timestamp/test_timestamp.test:119,139`,
`function/generic/test_if_null.test:15`, `function/generic/test_if.test:20`.

## R11. Ordering comparisons of lists

- **Substrait:** `lt(x, y)` (and `gt`, `lte`, `gte`) takes `any1`, and
  "if either/both of `x` and `y` are `null`, `null` is returned"; it does
  not define an order on lists.
- **Lean:** `[1, 2] < [1, 3]` is NULL on every row. NULL on non-NULL inputs
  is a **deviation**. Which order applies, element-wise or none (refuse), is
  **pending**.
- **DuckDB (native):** element-wise, lexicographic.

Evidence: `types/list/list_comparison.test:136-186`,
`types/list/list_null_members.test`, `join/test_nested_inequality.test:57,94`.

## R12. `fp32`

- **Substrait:** `fp32` and `fp64` are distinct types with their own impls.
- **Lean:** one double kind, so `2e38::FLOAT / 0.1` is `2e39`. A
  **deviation** of width (principle 3).
- **DuckDB (native):** `FLOAT` is 32 bits: `inf`, and `1e308::FLOAT` fails
  to convert.

Evidence: `overflow/double_float_overflow.test:43`, `cast/double_float_cast.test`,
`overflow/test_numeric_overflow.test:11`, `optimizer/…/test_float_identity.test:123`.

## R13. `substring` with a negative start

- **Substrait:** `negative_start: [WRAP_FROM_END, LEFT_OF_BEGINNING, ERROR]`.
- **Lean:** `LEFT_OF_BEGINNING`, as DataFusion does
  (`substring('hello' FROM -2 FOR 2) = ''`). **Pending.**
- **DuckDB (native):** `WRAP_FROM_END` (`'lo'`). `LEFT_OF_BEGINNING` needs a
  shim, `CASE WHEN start < 1 THEN substring(s, 1, GREATEST(start + len - 1, 0)) ELSE substring(s, start, len) END`.
  `ERROR` needs a guard.

Evidence: `function/string/test_substring.test:129,207`, `types/string/test_unicode.test:31-41`.

## R14. `-0.0` and `0.0`

- **Substrait:** `fp64` is IEEE. The spec says nothing about grouping or
  ordering `-0.0`.
- **Lean:** one zero (#89), so `1.0 / -0.0` is `inf`, not IEEE's `-inf`.
  **Pending**, with #89.
- **DuckDB (native):** `-0.0` sorts before `0.0`, and `1.0 / -0.0 = -inf`.

Evidence: `order/…:28` (`SELECT v, 1.0 / v FROM zero_probe`).

## Frontends: DuckDB's SQL and DataFusion's

These are about how SQL text becomes a plan, not about what a plan means.
The replay translates DuckDB's SQL to DataFusion's and checks the
translation against DuckDB (`sverify.slt.translate`).

- **F1.** In DuckDB, `/` on integers is float division and `//` is integer
  division; the setting `integer_division` switches `/`.
- **F2.** DuckDB puts NULLs last in both directions; DataFusion puts them
  first for `DESC`. The replay writes the order out and follows
  `SET default_null_order`.
- **F3.** DuckDB types an integer literal as the narrowest type that holds
  it (R1).
- **F4.** DuckDB has collations (`NOCASE`, `NOACCENT`), macros that shadow
  functions, and case-insensitive identifiers. The replay skips queries
  under a collation or macro, and follows the identifiers.

## sverify: written plans, the producer and the harness

### S1. The written plan types literals by their value (#96)

`LEAST(DATE '1992-01-01', …)` on DuckDB returns `7670`, and timestamp and
interval literals come back as integers. Evidence:
`function/generic/test_least_greatest.test:69-95`, `types/date`,
`types/timestamp`, `types/interval` (the `engine` side).

### S2. The written plan computes narrow integers in 64 bits

`100::TINYINT + 50::TINYINT` on the written plan gives 150 on DuckDB, while
DuckDB itself raises: `sql/duckdb.py` writes the arithmetic without the
narrow type. Under R1 this becomes "emit at the declared width". Evidence:
the `both` entries of `overflow.json`.

### S3. DataFusion's producer drops `VALUES` rows

DataFusion 51 writes `FROM (VALUES …)` as an empty virtual table. The
replay refuses these plans (`producer: VALUES written as an empty virtual table`).

### S4. Decimal literals become doubles

DataFusion's SQL reads `99999999999999999999.99999` as a double, so
`100000000000000000000 > 99999999999999999999.99999` is false. Evidence:
`cast/decimal_float_cast.test:10`.

### S5. What the replay cannot run

Most refusals are DuckDB features outside the model (structs, maps,
decimals, blobs, `range()`, `PIVOT`, DuckDB-only functions), or SQL that
sqlglot or DataFusion's SQL cannot read. The replay inlines only the values
`sverify.testing.literal` writes, so tables holding structs, decimals or
blobs are refused (`tables: no Lean literal`). Expected errors that are
DuckDB binder or parser errors are skipped (`DuckDB frontend error`).

### S6. DataFusion's SQL frontend plans another query

In these cases `Rel.eval` and DuckDB running the written plan agree with
each other, and both differ from DuckDB, because the plan DataFusion writes
is not the query. Each is a plan sverify checks for a query the user did
not write.

- `EXCEPT ALL` is planned as a left anti join, which loses multiplicities:
  `[1, 1, 2, 3] EXCEPT ALL [1, 3]` gives `[2]`, not `[1, 2]`
  (`setops/test_pg_union.test:339,350`).
- `FETCH FIRST n ROWS ONLY` is dropped: the plan has no limit
  (`parser/fetch_first.test`).
- The Substrait producer drops `DISTINCT` and `FILTER (WHERE …)` of a
  window aggregate: `COUNT(DISTINCT s) OVER (…)` counts every row
  (`window/test_window_distinct.test:76`,
  `window/test_naive_aggregation.test:204`,
  `window/test_streaming_window.test:223`).
- `GROUP BY k, k` writes two grouping expressions, and the projection above
  reads the aggregate's columns shifted by one
  (`aggregate/group/test_group_by.test:149`). Either the producer or Lean's
  reading of a repeated grouping expression is wrong; this needs reading.
- `SELECT *` of a `NATURAL JOIN` keeps both copies of the join columns
  (`catalog/case_insensitive_using.test:123-138`).
