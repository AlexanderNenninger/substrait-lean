# DuckDB characterization

The replay of DuckDB's sqllogictests through sverify (`python -m sverify_dev.slt`)
and the fuzz findings against DuckDB (`python -m sverify_dev.duckdb_fuzz`), one
ledger per area of DuckDB's `test/sql/`, for epic #185, and the probes of DuckDB's functions (`python -m sverify_dev.probe`,
[probes.json](probes.json)). The facts drawn from them are one JSON document
each in [facts/](facts/), with their provenance (`python -m sverify_dev.facts`
checks them).

The quoted tests (queries and expected results) are © Stichting DuckDB
Foundation, MIT-licensed ([LICENSE-duckdb](LICENSE-duckdb)), taken from
[duckdb/duckdb](https://github.com/duckdb/duckdb) at `v2.0.0` (commit
`d54cbbe3df17e8e5ce68312f483b4155836112aa`), the version `python/uv.lock`
pins; each ledger records it (`"duckdb"`, `"source"`). The ledgers and
facts themselves are MPL-2.0, like the rest of the repository.

## How the facts are judged

What DuckDB's own sqllogictests (`test/sql/` at `v2.0.0`) and the fuzzer
say, judged against the reference model's principles (#185, "Principles for
the reference model"):

- `Rel.eval` means Substrait's semantics: each function's extension
  YAML, including its options.
- Where Substrait leaves a choice open, the reference takes the least
  surprising one that every backend can emulate.
- DuckDB's profile is a diff against that reference.

Substrait here is the spec at `v0.108.0`: `extensions/functions_arithmetic.yaml`,
`functions_comparison.yaml` and `functions_string.yaml`.

The evidence is ledger entries (`<area>.json`, by test file and line), fuzz
findings (`fuzz__<target>.json`) and probe verdicts ([probes.json](probes.json)).
The ledgers, the probes and the summary table below are generated by
`python -m sverify_dev.slt`, `python -m sverify_dev.duckdb_fuzz` and
`python -m sverify_dev.probe`. The facts are written by hand from them, one
document per finding in [facts/](facts/), in the format of
[fact.schema.json](../fact.schema.json). A fact's `provenance` lists each check:
when, by which method and tool, and its evidence (a test at DuckDB's commit, a
ledger, a probe construct of `probes.json`, a SQL repro with its output). The
R15 facts are the probe verdicts: `Profile.duckdb` (`SubstraitLean/Profile.lean`)
is seeded from them, and `probes.json` stays the harness's output, which
`tests/test_probe.py` checks is current.

## What the plans say, and what the reference does

The plans come from DataFusion 51's SQL producer. They set no function
options and no extension URNs: a call is `add`, `divide`, `modulus`, … by
name, with argument and output types. Casts do carry
`failureBehavior: FAILURE_BEHAVIOR_THROW_EXCEPTION`. So every function
option below is omitted, and the reference's defaults apply, as decided on
#185 ("Decided: what the reference does when a plan omits an option"):

- an omitted `overflow` is ERROR, at the declared width `i8`…`i64`
  (`SILENT` and `SATURATE` only when the plan asks);
- an omitted `on_division_by_zero` is ERROR, for `divide` and
  `modulus` (`NULL` only when the plan asks);
- an error means "may raise", and a rewrite is proved as a refinement:
  it may raise in fewer cases, never answers differently, and never raises
  where the original did not.

In sverify, "may raise" is `verify`'s error issues (`Rel.mayIssues`,
`SubstraitLean/Safety.lean`): on a row where an error issue fires,
`Rel.eval`'s value is not the answer. So a finding is a deviation when
`Rel.eval` and `verify` together disagree with the reference: either
`Rel.eval` gives a different answer on a row where nothing may raise, or
`verify` calls an error a warning, or misses it. It is no finding when
`verify` reports the error that the reference raises.

A few points are not covered by the decisions and stay open:
`modulus`'s `division_type`, the rounding of casts to integers, `substring`'s
`negative_start`, `-0.0`, the order of lists, and `avg`'s output type. For
each, the finding says what Lean and DuckDB do; most of them make no
difference between the two.

For each finding, the DuckDB diff says whether DuckDB, under its default
settings, gives the reference result natively, needs a shim, or must be
refused.

In the earliest draft these were M1–M7: M1 is R1 and R6, M2 is R2, R3 and
R5, M3 is R8, M4 is R4, M5 is R7, M6 is R10 and M7 is R11.

The counts come from matching the ledgers' `disagree` entries (their SQL,
and their expected and actual results) against each finding. One entry can
show two findings, and about 40 of the 424 disagreements are not assigned
yet (intervals of months, the `UUID` type).

## The DuckDB diff, as a table

How a Substrait call is emitted for DuckDB 2.0.0 so that it gives the
reference result. The first row of each function is the reference default
(an omitted option); the others apply when a plan sets the option. "Native"
means DuckDB's own operator, under its default settings.

| Function (types) | Option | Value | DuckDB |
|---|---|---|---|
| `add` `subtract` `multiply` `negate` `abs` (`i8`…`i64`) | `overflow` | `ERROR` (default) | native, at the declared width |
| | | `SILENT` | shim: `HUGEINT`, wrap to width |
| | | `SATURATE` | shim: `HUGEINT`, clamp |
| `divide` (`i8`…`i64`) | `on_division_by_zero` | `ERROR` (default) | native; guard if `error_on_division_by_zero` is off |
| | | `NULL` | shim: `CASE WHEN y = 0 THEN NULL` |
| | `overflow` (`MIN / -1`) | `ERROR` (default) | native |
| `modulus` (`i8`…`i64`) | zero divisor | `ERROR` (default) | native, but `MIN % -1` raises (duckdb-R15); guard if the setting is off |
| | `division_type` | open | `TRUNCATE` native; `FLOOR` shim |
| `modulus` (`fp64`) | zero divisor (none in Substrait) | `ERROR`, as on integers | guard; native on finite operands, NaN and ±inf written out |
| `divide` (`fp64`) | `on_division_by_zero` | `ERROR` (default) | guard (native with `ieee_floating_point_ops` off) |
| | | `IEEE` | native, but `±inf / ±inf` is NaN (duckdb-R15) |
| | | `NULL`, `LIMIT` | shim |
| `sum` (`i64`) | `overflow` | `ERROR` (default) | shim: `CAST(SUM(x) AS BIGINT)` |
| | | `SILENT`, `SATURATE` | shim on the `HUGEINT` sum |
| `cast` to `i8`…`i32` | `failureBehavior` | `THROW_EXCEPTION` | native |
| | | `RETURN_NULL` | native (`TRY_CAST`) |
| `cast` `fp64` → integer | rounding | truncate | shim (`trunc` first) |
| `substring` | `negative_start` | `WRAP_FROM_END` (default) | native; the SQL normalizes the start |
| | | `LEFT_OF_BEGINNING` | shim |
| `lt` … on lists | | lexicographic | shim (`list_lt`: NULL where a NULL element decides) |

The guard for `error_on_division_by_zero = false` is
`CASE WHEN y = 0 THEN error('division by zero') ELSE … END`. With the
default setting, every default row is native, except integer `sum`, whose
accumulator is wider than the reference's.

DuckDB settings the diff depends on: `error_on_division_by_zero` (default
true, integers only), `ieee_floating_point_ops` (default true: doubles),
`integer_division` (frontend only), `default_null_order` (frontend only).

## sverify: written plans and the harness

S3, S4 and S6 are DataFusion's: [../datafusion/facts/](../datafusion/facts/).

### S1. The written plan types literals by their value (#96)

`LEAST(DATE '1992-01-01', …)` on DuckDB returns `7670`, and timestamp and
interval literals come back as integers. Evidence:
`function/generic/test_least_greatest.test:69-95`, `types/date`,
`types/timestamp`, `types/interval` (the `engine` side).

### S2. The written plan computes narrow integers in 64 bits

`100::TINYINT + 50::TINYINT` on the written plan gives 150 on DuckDB, while
DuckDB itself raises: `sql/duckdb.py` writes the arithmetic without the
narrow type. Under duckdb-R1 this becomes "emit at the declared width". Evidence:
the `both` entries of `overflow.json`.

### S5. What the replay cannot run

Most refusals are DuckDB features outside the model (structs, maps,
decimals, blobs, `range()`, `PIVOT`, DuckDB-only functions), or SQL that
sqlglot or DataFusion's SQL cannot read. The replay inlines only the values
`sverify.testing.literal` writes, so tables holding structs, decimals or
blobs are refused (`tables: no Lean literal`). Expected errors that are
DuckDB binder or parser errors are skipped (`DuckDB frontend error`).

## The replay ledgers

Each result is `agree` (Lean's `Rel.eval` gives the expected result, and so
does DuckDB running the plan Lean writes, unless the writer refuses the plan:
the table counts those agreements, checked by oracle A only, apart),
`disagree` (`side`: `lean`, `engine`
or `both`), `refused` (sverify does not plan the query) or `skipped` (it
needs an extension, a setting, a second connection, …). Rerun with:

```bash
cd python && uv run python -m sverify_dev.slt --jobs 2
```

Totals over 46367 queries of DuckDB's tests: 7117 agree, 407 disagree, 26169 refused, 12674 skipped (1034 files skipped whole). The fuzzer checked 42306 random queries on homelab and kept 17 distinct disagreements (`fuzz/*`).
